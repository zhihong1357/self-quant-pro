## 背景

规则 12 要求"提出者不审自己"。G1 前两条验收标准的证据（`tests/test_pit.py`）原本都是作者自己写的测试，等于自己出题自己考。所有者于是把时点接口交给 Gemini 做红队审查，Gemini 提出 8 条发现。智能体逐条对照代码核实：8 条全部属实，第 2、3 条属于设计上的限制，处理方式见下面的"决定"。

| # | 发现 | 核实 | 处理 |
|---|---|---|---|
| 1 | 分段边界直接读工作区的 `U1.toml`，改了它就能绕过所有守卫 | 属实 | 分段和注册、批准一样，只认 main。main 上没有研究宇宙，就什么都不读 |
| 2 | 同一个进程里，可以绕过 `table()` 直接读存储，或者改对象的内部状态 | 属实；进程内的类本来就做不到强隔离 | 内部属性改为私有，分段改为不可变。硬边界见决定第 1 条；静态检查见后果 |
| 3 | `origin/main` 只是本地引用，可以伪造；本地的拒绝记录可以被抹掉 | 属实 | 引用写全名。确认集、前向和金库只能在 GitHub Actions 的 main 上读（决定第 2 条）。拒绝记录同时写进存储桶，那里只增不改 |
| 4 | 时区不是 UTC 时，会按当地月份挑分块，少读数据 | 属实：只会少读，不会多读 | 一律先换算成 UTC |
| 5 | 只要状态不是 draft 就放行，也不检查研究宇宙 | 属实 | 只有 registered 和 confirmed 能读，研究宇宙必须一致 |
| 6 | 缓存不是原子写入，也没有完整性校验 | 属实 | 改成原子写入。读过的每个分块都按内容算指纹，缓存文件被换掉，画像的输入指纹就会变 |
| 7 | 分块编号超过 99、start 晚于 end、各段没有首尾相接 | 属实，影响小 | 都已修。"只往前多读一个月"的假设写进了代码注释 |
| 8 | 测试有缺口 | 属实 | 时点接口的测试从 8 个增加到 31 个（含第二轮） |

修好以后，所有者请 Gemini 复查。结论是：第 1、4、5、8 条已修好；第 2、3、6、7 条部分修好。另外有 7 条新发现，主要出在这次新加的代码上。智能体逐条核实，全部属实并修复：

| # | 新发现 | 处理 |
|---|---|---|
| 1 | 拒绝记录写不进存储桶时，错误被悄悄吞掉；在 GitHub Actions 里，这条记录就彻底丢了 | 不再吞掉。写失败会打印出来，并写进拒绝的报错信息。记录里加上时间、运行编号和代码提交 |
| 2 | "是不是在 main 上"只看两个环境变量；用 `pull_request_target` 触发时，这两个变量也满足 | 加了两个条件：触发方式必须是定时或手动（和存储桶身份的规则一致）；当前运行的代码必须就是 main 上的那个提交 |
| 3 | 本地账本写失败时，存储桶那份不写，而且抛出的不是"拒绝" | 两份分别写，各自出错都记下来，最后一定抛出"拒绝" |

| 6 | 时区换算和 start、end 的顺序检查移进了 `table()`，直接调用公开的 `authorize()` 就绕过了 | `authorize()` 改为内部方法，换算和检查都在它里面做 |
| 7 | 缓存写入出错时临时文件没有清理；没有检查单个段是不是空的 | 都已修 |

第一轮第 7 条里"只往前多读一个月"的说明，这次才真正写进代码注释，补上了。`build.py` 里分块编号的匹配上一轮已经改好，只是第二轮的复查包没有附这个文件。

## 决定

1. **写明信任边界。**
   - 时点接口防的是诚实的错误，并且让故意绕过在代码审查里看得见；同一个进程里存心作弊的代码，它挡不住。
   - 真正的硬边界是存储桶的凭据：只有 main 上的工作流（代码已经由所有者合并）和所有者本人能读；智能体的环境里没有凭据。
   - **所有者不要把自己的谷歌云登录交给任何智能体。**
2. **读确认集、前向和金库，只能在 GitHub Actions 里运行。** 触发方式必须是定时或手动，运行的必须是 main 上的提交。这样日志公开、代码已经合并、凭据只在那里。探索集在哪里都能读。
3. 时点接口的其他改动见上表。另外两处顺带修了：
   - 画像文件标明 UTF-8 编码，修好浏览器里的乱码；
   - 画像的输入指纹改成按内容算；摘要表里的中位数改成"不含默认费率的年化中位数"，因为原来的中位数被默认费率淹没了。

## 后果

- G2 的运行框架加一条静态检查：研究代码只能通过 `sqp.data.pit` 读数据，不能直接导入存储层或谷歌云的客户端。这是第 2 条发现的长期修法，写进路线图 G2。
- 画像的代码变了，所以合并后要再跑两次（第一次写入，第二次应当报告"重算一致"），新结果和新指纹以那两次为准。
- 以后每个阶段验收之前，都请一个和作者不同的模型做一次红队审查。审查包的做法和这次一样：在一个文件里写明要求，附上相关代码的全文。
