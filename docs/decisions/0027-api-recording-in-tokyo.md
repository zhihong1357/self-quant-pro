# 0027 Binance 交易接口的数据在谷歌云东京区录；研究的前向数据先用公开归档；实盘之前用自己录的数据重新估计和验证

- 日期：2026-11-26
- 提出：Claude（Opus 5.5），做完决策 0026 第 5 条要求的条款核对之后提出。所有者 2026-11-26 选定"现在就在东京录"，合并即批准

## 背景

决策 0026 第 5 条要求：A 和 B 选完之后、G2 结束之前，核对 Binance 接口数据的条款，每天录资金费率和 K 线，再注册 2 到 3 个只靠前向数据检验的假说。理由有两个：前向证据要从注册那天才开始算；实盘能用的数据（决策 0011 第 4 条）只能从开始录的那天攒起。

A 和 B 已经各估计过一次（运行 45765535965）：T-0004（A）和 T-0005（B）都判"不通过"。按决策 0026，两个都不花确认集，改等前向数据。

2026-11-26 核对了以下条款（这不是法律意见）：

| 文件 | 版本 | 和本项目有关的条文 |
|---|---|---|
| Binance 用户条款 | 生效日 2026-10-27 | 第 2.1 条：使用者不能位于禁止国家名单上的地区，也不能位于使用 Binance 服务违法的地区；第 14.1.2 条：接口另有接口条款，并且要经过 Binance 同意；第 27 条：许可只限非商业的个人使用或内部业务使用；第 33.7 条：条款预期用户会用 Binance 的技术搭建自动交易系统，后果由用户自己承担 |
| 禁止国家名单 | 2026-01-05 版 | 第 1 组：美国（人在美国，或者是美国居民、美国公民，都不行）；第 2 组：加拿大、荷兰；第 3 组：古巴、朝鲜、伊朗，以及几个受制裁的地区 |
| Vision 数据条款 | 1.0，2026-08-26 更新 | 第 2.3 条：任何个人或机构都可以免费使用；第 2.4 条：由数据得出的图表、模型、指标受同样的条款约束；第 4.1 条：允许纯个人、非生产用途的历史回测；第 4.2 条：不得用于实盘自营交易（决策 0011 已经记下） |

由此得出四点：

1. **GitHub 的服务器上录不了。** 我们的定时任务跑在 GitHub 的服务器上。这些服务器在美国，而美国在禁止名单的第 1 组；Binance 的主接口本来也拒绝来自美国的访问（[代际传承](../lineage.md)第 6 节）。
2. **谷歌云的东京区（asia-northeast1）录得了。** 日本不在禁止名单上；公开行情接口不需要 Binance 账号，也不需要密钥。
3. **实盘要用自己录的数据。** 公开数据站的数据只能做研究，由它得出的模型也受同样约束；交易接口的数据按用户条款第 27 条可以做非商业的个人使用。所以将来实盘用的模型，要用自己从接口录的数据重新估计参数、重新验证一遍（决策 0011 第 4 条的第二条路）。录得越早，到时能用来验证的数据越多。
4. **有些数据不录就再也拿不到。** 例如持仓量的历史，接口只保留最近 30 天；已经下架的合约，接口也查不到了。

所有者 2026-11-26 还说明：系统按国际通用设计，他也可能换地方住，不要按他现在的居住地来限制；研究阶段尽量全覆盖。

考虑过的做法：

| 做法 | 要做什么 | 风险 |
|---|---|---|
| 在 GitHub 的服务器上录 | 新增一个每日工作流 | 会被拒绝；就算连得上，也违反用户条款第 2.1 条 |
| 在所有者家里的电脑上录，开 VPN | 电脑一直开着，VPN 不能断；电脑上放一个能写存储桶的凭据 | 凭据放在家用电脑上不安全；电脑一关数据就断；用 VPN 绕开当地的封锁 |
| 在谷歌云东京区开一台虚拟机 | 建虚拟机、装环境、定时运行 | 连同公网地址每月约 10 美元（推测）；要维护操作系统；对外开着登录端口 |
| **在谷歌云东京区建一个定时任务（采用）** | 一键设置脚本：Cloud Run 任务（只在运行时存在的容器）加 Cloud Scheduler（定时器） | 在免费额度之内；没有对外开放的端口，没有要维护的系统 |
| 不录，等 G5 | 什么都不做 | 只保留 30 天的数据和已下架合约的数据补不回来 |

## 决定

1. **在谷歌云东京区建一个每天运行一次的录制任务**，从 Binance U 本位合约的公开行情接口录数据，原样存进存储桶：只增不改，每份都记 SHA-256（和[决策 0018](0018-mirror-binance-vision.md) 一样）。第一版录：合约列表和状态的快照、资金费率、1 小时 K 线、持仓量的历史。不用 Binance 账号和密钥，也不碰任何下单接口（规则 1）。遵守接口公布的频率限制，被限流就停下。
2. **另开 PR 实现**：录制代码、测试、一键设置脚本（所有者在 Cloud Shell 里运行，和 G1 的做法一样），以及中文的操作步骤。经 Gemini 审查后合并。
3. **规则 10 的例外，只放开这一个任务。** 规则 10 写的是"G5 起"才部署到谷歌云。录制任务属于数据采集，和 GitHub 上每周的数据同步工作流同一类：它每次运行时从 main 取代码，而 main 只能经由检查全绿、所有者合并的 PR 改动，这就是它的审批。G5 的生产计算仍然按规则 10，走 production 环境审批。
4. **研究的前向数据先用公开归档**在注册日之后新发布的部分（决策 0012 第 2 条）；录制任务攒够数据之后再接进来。第一个只靠前向数据检验的假说现在就可以注册，不等录制任务。路线图 G2 的"每日前向数据"由录制任务提供，公开归档的逐日文件不再需要。
5. **实盘之前**：用哪个交易场所，按所有者当时的居住地核对（[合规](../compliance.md)第 2 节第 1 项）；用到的模型，按上面第 3 点用自己录的数据重新估计和验证。
6. 合规表加上 Binance 用户条款这一行。

## 后果

- 谷歌云第一次用到按量计费的服务（Cloud Run）。按 G1 的设置说明，同时建封顶预算。预计每月约 0 美元（Cloud Run 任务和 Cloud Scheduler 的免费额度之内，推测，置信度中），由每月 10 美元的赠金兜底，预算提醒照旧。
- 所有者要做的：录制 PR 合并后，在 Cloud Shell 里运行一次设置脚本（约 10 分钟）。
- 如果 Binance 以后拒绝东京区的访问，任务会报错停下，不影响研究；那时再评估别的区域。
- 公开归档和自己录的数据会有一段重叠，可以互相核对，查出两边的差异。
