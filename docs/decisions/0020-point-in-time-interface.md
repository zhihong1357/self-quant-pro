# 0020 时点接口：只能读到当时已经知道的数据；金库守卫

- 状态：已接受
- 日期：2026-11-25
- 提出：Claude，所有者合并即批准

## 背景

G1 的验收标准有三条，这个决策落实前两条：

- 前视在接口层面写不出来，并且有测试证明；
- 没有批准就读金库，会被拒绝并留下记录；
- 探索集画像能一条命令重算（下一步）。

月度表的每一行都带"何时可知"（`knowable_time`，决策 0019）。缺的是一个唯一的读取入口：它要按这一列过滤，并在读之前检查要读的时段属于哪一段数据。

## 决定

1. **唯一入口。** 研究代码读研究用的月度表，只能通过 `PointInTime.table(数据集, end=时刻, start=时刻)`（`src/sqp/data/pit.py`）。
   - 它只返回 `knowable_time` 在 `[start, end]` 之间的行，两端都包含，绝不返回 `end` 之后才知道的数据。
   - 想看更晚的数据，只能把 `end` 往后调；而 `end` 每次都要经过下面的检查。
2. **一行数据属于它"变得可知"的那一段。** 例如 2024-01-31 23:00 那根 K 线在 2024-02-01 00:00 才收盘，它属于确认集，不属于探索集。
3. **按段放行。**

   | 要读的时段碰到 | 需要什么 |
   |---|---|
   | 探索集，以及更早的数据 | 不需要什么 |
   | 确认集、前向数据 | 一个已经注册的假说（`purpose`） |
   | 金库 | 已经注册的假说，加上所有者对这个假说的金库批准 |

4. **注册和批准都以合并为准。** 只读 `origin/main` 上的文件，不读工作区。合并是所有者的签名，工作区谁都能改。账本的哈希链断了，就什么都不批准。
5. **金库批准的格式。** 由智能体在 PR 里用 `sqp ledger append` 往 `registry/ledger/approvals.jsonl` 追加一条：

   ```json
   {"type": "vault", "universe": "U1", "hypothesis": "H-0001", "note": "为什么现在动用金库"}
   ```

   所有者合并这个 PR，就是批准。
6. **被拒绝的请求要记账。** 每次被拒绝，都往 `registry/ledger/refusals.jsonl` 追加一条：数据集、时段、用途、原因，不含任何数据。
   - 这会让工作区出现改动，必须在下一个 PR 里提交。
   - 提交以后不能删，账本只追加。
   - 在 GitHub Actions 里被拒绝时，运行会直接失败，日志里看得到。
7. **时间必须带时区（UTC）。** 不带时区的时刻一律报错，免得差几个小时、悄悄用到未来的数据。
8. **本机缓存。** 可以把读过的表缓存在本机。存储桶里的对象只增不改，所以缓存永远有效，也省流出流量。

## 后果

- G1 验收标准的前两条有了测试：`tests/test_pit.py`。
- 下一步：探索集画像，只通过这个接口读数据，结果写进私有存储桶。
- 本 PR 同时更新：规程第 2 节（批准的格式和以合并为准）、架构第 2 节、交接记录。
