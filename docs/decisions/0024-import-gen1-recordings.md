# 0024 每天导入第一代的录制数据；只读令牌放在只许 main 使用的环境里

- 状态：已接受
- 日期：2026-11-25
- 提出：Claude（Opus 5.5）。所有者 2026-11-25 选定"只读令牌，定期导入"，合并即批准

## 背景

第一代还在两个私有仓库里，每天录三样无法重新获取的数据（[代际传承](../lineage.md)第 2 节）。2026-11-25 用 GitHub 接口量过：

| 仓库和分支 | 录什么 | 现在的大小 |
|---|---|---|
| `fakeout-backtest` 的 `main`，`data/gex/` | Deribit 全量期权每日快照（BTC、ETH），2026-10-26 起 | 62 个文件，约 0.9 MB |
| `orderflow` 的 `gex-data` | Deribit GEX 快照，2026-10 起 | 1 个文件，不到 0.1 MB |
| `orderflow` 的 `lab-data` | 基差、资金费率、期权平价、美股期权流指标的定时快照，2026-11-12 起 | 约 3.5 MB |

两个仓库连同全部历史分别约 12.9 MB、4.7 MB。决策 0023 要求 G2 开始两周之内导入。

有三个限制：
- 录制每天都在继续，所以要定期导入，不能只搬一次；
- 第三代工作流自带的令牌只能读本仓库，读不到这两个私有仓库；
- 智能体没有存储桶凭据（决策 0022）。

## 选项

| 选项 | 代价 |
|---|---|
| 只读令牌，定期导入（选定） | 所有者建一个令牌，约 5 分钟；令牌到期要换 |
| 只导入一次 | 不用令牌，但以后每次更新都要所有者手动上传 |
| 第三代自己录 | 不用令牌，但要写一套录制程序，挤占 G2 的运行框架 |

## 决定

1. **怎么存**：存成 git bundle，也就是 git 自带的打包格式，含历史。
   - 每个分支第一次存完整历史，以后只存上次导入之后新增的提交。
   - 对象放在 `raw/gen1/<仓库>/<分支>/<提交>-from-<上次导入的提交>.bundle`，清单放在 `manifests/gen1/<运行>.jsonl`。
   - 最新的一份清单列出每个分支导到了哪个提交，以及每个对象的 SHA-256。
   - 存储桶只增不改。

   存历史而不是只存最新的文件，有三个理由：
   - 第一代的文件有的是往后追加的，有的可能被覆盖；
   - 历史里记着每一行数据是什么时候推上 GitHub 的，以后做时点表时，这就是"最早何时可知"的依据；
   - 全部历史也只有十几 MB，git 自己会压缩。
2. **多久一次**：每天一次，定时运行，也可以手动触发。没有新提交就什么都不写。
3. **报警**：报警时运行失败，GitHub 会发邮件给所有者。三种情况会报警：
   - **断更**：每个分支在 `registry/sources/gen1.toml` 里有 `stale_after_days`。看的是数据所在路径的最近一次提交，不是整个分支的，超过这么多天就报警；
   - **历史被改写**：上次导入到的提交已经不在现在的历史里。这时另存一份完整的历史，旧的照样保留；
   - **超出存储上限**（`config/storage.toml`）：这次不存。
4. **令牌**：细粒度个人令牌，有到期日，只能读 `fakeout-backtest` 和 `orderflow` 两个仓库的内容（Contents: Read-only）。
   - 它放在本仓库环境 `gen1` 的环境密钥 `GEN1_READ_TOKEN` 里，环境 `gen1` 只许 `main` 使用。这样别的分支上的工作流拿不到它。智能体会推分支，普通的仓库密钥挡不住这一点。
   - 这是对规则 2 的补充：只给 GitHub Actions 用的 GitHub 令牌，放只许 main 使用的 GitHub 环境密钥。规则 2 的其余部分不变：钱相关的密钥由所有者自己保管。AGENTS.md 规则 2 的文字同步补上这一句。
5. **只读第一代，不改第一代**：不在第一代的仓库里加任何东西。
6. **条款**：上游的条款还没核对，包括 Deribit 公共接口、CBOE 延迟行情等。现在只是私有保存；按决策 0023，哪个假说要用，就在注册前核对哪个。

新增的工作流：`.github/workflows/gen1-import.yml`。

还原一个分支：按清单的顺序，把它的每个 bundle 取进一个空的裸仓库：

```
git init --bare restore.git
git -C restore.git fetch <bundle 文件> '+refs/*:refs/*'
```

## 独立审查

所有者请 Gemini 审查了这个 PR（2026-11-25），一共 3 条发现：

| # | 发现 | 处理 |
|---|---|---|
| 1 | 用了环境 `gen1` 之后，GitHub 签发的身份令牌里 `sub` 会变；如果谷歌云按 `sub` 授权，就连不上 | 核实后不成立：`scripts/gcp/setup-storage.sh` 里的条件和存储桶授权只看仓库编号、所有者编号、`ref` 和触发方式，不看 `sub`。合并后的第一次手动运行会再确认一次 |
| 2 | 上一次运行存完 bundle、还没写清单就失败了，重试时会把剩余空间算少；临近上限时会一直误报 | 属实，已修：对象已经存在就直接复用，不再检查、也不再扣减剩余空间 |
| 3 | 一个分支出错（比如被改名）会中断整轮，前面存好的分支也不写清单 | 属实，已修：每个分支单独处理，出错的记一条报警，其余照常归档、写清单 |

## 后果

- 所有者要做一次：建令牌、建环境 `gen1`、放进环境密钥，步骤见[所有者简报](../owner-brief.md)第 8 节。要先做完这些再合并，否则定时运行会自己建一个没有分支限制的 `gen1` 环境。
- 令牌到期时，导入会失败，GitHub 发邮件；按所有者简报第 8 节换一把新的。
- 存储：第一次约十几 MB，以后每天几 KB 到几十 KB。
- 以后要用这些数据时：从 bundle 还原，按提交时间定"最早何时可知"，做成研究表。这一步另开决策。
- 重新考虑的时机：第一代停止录制，改由第三代自己录；或者第一代的仓库要删。
