# 0015 G1 现在开始，不等 finance-research；谷歌云只开存储

- 状态：已接受
- 日期：2026-11-24
- 提出：所有者（"也许我们可以先暂时忽略 finance-research，我不想闲置时间等 12 月 8 日然后才开始决定 G1"），Claude 补充执行细节

## 背景

G0 已经验收，PR #1–#5 都在 2026-11-24 合并。路线图把"所有者对 finance-research 的决定（约 2026-12-08）"列为 G1 的前置条件，理由是 G1 可能接管它的数据代码。

这个前置其实没有必要。0001 已经规定前两代只作参考、不搬代码，需要的实现按本仓库的约定重写并配测试。不管 finance-research 以后继续还是停掉，第三代的数据层都要从头写。多等 14 天，只会让 G1 的 3 周时间盒白白往后推。

2026-11-24 同时核对了谷歌云的两处事实：

1. Google AI Pro 每月附带 10 美元谷歌云赠金。可以在 Google AI Studio 里领取（2026-11-13 上线），前提是有谷歌云结算账号。
2. 封顶预算（spend cap）已经正式发布。到顶后，它暂停指定项目里的指定按量服务，例如 Gemini API、Cloud Run；下个月自动恢复。但它不暂停存储这类持续计费的资源。所以 0003 和 0010 说的"到顶自动暂停"，对存储不成立。

## 决定

1. `STAGE` 从 G0 进入 G1，现在开始。finance-research 的去留和第三代脱钩，所有者什么时候决定都行，不影响 G1。
2. G1 的数据层从头写，只参考第二代的设计（时点接口、金库守卫、数据源登记），不搬代码。
3. 谷歌云按 `docs/gcp-setup.md` 开通，只开存储：
   - 一个私有存储桶：us-central1，统一权限，禁止公开访问。
   - 不建服务账号，改用直接的 Workload Identity Federation。只放行本仓库 `main` 分支上定时或手动触发的工作流；仓库和所有者都按 GitHub 不会复用的数字编号认，PR 触发的工作流拿不到身份。
   - 这个身份在存储桶上只有"新建对象"和"读对象"两项权限，不能删除，也就不能覆盖。只增不改由谷歌云的权限强制，不只靠我们自己的代码。
   - 这是对 0010 第 1 条"只给创建对象的权限"的补充：检查文件是否已经存在、计算数据画像，都需要读权限；读权限不影响只增不改。
   - 预算提醒：每月 10 美元，按原价计算（不扣赠金），花到 1、5、9、10 美元时发邮件。
4. 存储费用由三层控制，不靠封顶预算：
   - 数据量本身很小：最小切片压缩后估计不到 1 GB（研究可行性地图第 4 节），在每月 5 GB 的免费额度之内。
   - 代码自己设上限：上传前先检查存储桶的总量。
   - 预算提醒。

   封顶预算等 G5 用上 Cloud Run 时再建。
5. 谷歌云开通之前，G1 的代码先用本机存储后端开发和测试，不等谷歌云。

## 后果

- 本 PR 同时更新 `STAGE`、路线图、所有者简报、成本护栏、架构、宪章、代际传承和交接记录；0001、0003、0010 的状态行标注被本决策修改的地方。
- 所有者要做一次谷歌云设置，约 15 分钟，步骤见 `docs/gcp-setup.md`。做完把脚本最后打印的三行发给智能体。这三行都不是密钥。
- G1 的时间盒是 3 周，从 2026-11-24 算到 2026-12-15。超过两倍（2027-01-05）还没验收，就缩小范围或砍掉（路线图开头）。
- 需要重新考虑的情况：结算账号开不出来，例如没有能网上付款的卡。那样就把原始层和派生结果放在所有者的 Mac mini 上（私有，不进仓库），谷歌云推迟到 G5。
