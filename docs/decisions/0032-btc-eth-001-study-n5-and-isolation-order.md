# 0032 合入 btc-eth-001 研究代码、补齐 N5 与 stats.py 必锁，并将方案 B 期限提前至首次真实盲复现前

- 状态：已接受
- 日期：2026-11-28
- 提出：Antigravity（按模型 B 第四轮终审建议，经所有者拍板采用“组合做法 + 选项 1”）

## 背景

PR #29（决策 0031）通过模型 B 第四轮独立红队终审并获判“可合并”，完成了四联锁盲复现框架、结构性收紧的静态研究边界（方案 A）以及一次性批准代码指纹锁（L4）。同时，模型 B 在第四轮复审中提出三项紧接落地的加固与排序事项：

1. **N5（Polars 凭证与目录外连类名）**：收紧后的 `ALLOWED_MODULES` 仍必须保留 `polars`，但其顶层暴露了 `Catalog`（Unity Catalog 客户端，可按调用方给定的 URL 发起外连）与 `CredentialProviderGCP` / `AWS` / `Azure` / `Function`（实例化调用即可获取运行器实时云凭证），尚未列入 `research-boundary` 的 `OTHER_NAMES`。
2. **L4 覆盖面（`sqp.stats` 必锁）**：`btc_eth_001` 依赖 `sqp.stats` 中的统计原语；若 `src/sqp/stats.py` 仅为可选锁定，批准签发后仍可能改动统计内核而不触发校验失败。
3. **方案 B（子进程隔离运行）与首次真实盲复现的先后排序**：决策 0031 原先约定方案 B 在 PR #30 合并后立即启动、在任何新的研究代码合并前完成；但 `btc_eth_001` 本身就会在烧毁数据上消耗一次金库批准。考虑到 2026-11 币安月度归档通常在 2026-12 月初（约 3–7 天后）发布，正好可以利用这段等数据的空窗期先完成方案 B。

## 选项

1. **方案 B 与 `H-0010` 真实盲复现的排序**：
   - (a) 将方案 B 的期限前移至首次在烧毁数据上消耗金库批准运行 `btc_eth_001` 之前；
   - (b) 不卡方案 B，仅在 `btc_eth_001` 真实运行前先合入 N5 作为止血；
   - **(c) 组合做法（采用）**：本 PR 立即合入 N5 与 `stats.py` 必锁作为即时止血，同时按 (a) 将方案 B 的目标与硬期限前移至首次真实运行 `btc_eth_001`（`H-0010`）之前，利用 12 月初数据发布前的空窗期同步建成子进程隔离环境。
2. **N5 与 `stats.py` 必锁的合入载体**：
   - 保持已获模型 B 签字“可合并”的 PR #29（`3a62bbb`）原样合入，将 N5 与 `stats.py` 必锁随本 PR（PR #30）一并合入 `main`，既不破坏已签字提交，也能保证在任何真实金库批准签发前进入主线。

## 决定

1. **补齐静态研究边界的 N5 防御纵深**：在 `src/sqp/checks/research.py` 的 `OTHER_NAMES` 中加入 `Catalog`、`CredentialProvider`、`CredentialProviderGCP`、`CredentialProviderAWS`、`CredentialProviderAzure`、`CredentialProviderFunction`、`DeltaLake`，并把模型 B 第四轮 PoC 翻转为永久回归测试留在 `tests/test_redteam_pr29_round4.py`（同时扩充已知逃逸语料）。
2. **升级 L4 为三文件必锁**：在 `src/sqp/data/pit.py` 的 `approval_code_sha256_problems` 中，将盲复现模式金库批准的 `code_sha256` 必填键收紧为**恰好三个文件**：`src/sqp/research/studies/<study>.py`、`src/sqp/research/blind.py`、`src/sqp/stats.py`（不允许缺任一文件，也不允许额外未登记文件），静态 gate 与运行时 `check_vault_approval` 均按原始字节比对。
3. **合入 `src/sqp/research/studies/btc_eth_001.py` 与全链路合成彩排**：
   - 严格对齐 `myquant@e992b10`（`research/btc-eth-001/run_trial.py`）与 `H0001/v1.json` 口径：16:00 UTC 锚定 24 根完整 1h K 线聚合日线、`2023-01-01T16:00Z` 至 `2026-11-18T00:00Z` 日频窗口与 `2026-08-20T00:00Z` 至 `2026-11-18T00:00Z` 小时频窗口、单品种先算相邻对数收益再内连接（不前向填充、跨缺口作废）、三组带控制变量的偏超前滞后 HAC 检验（日频最大滞后 5、小时频最大滞后 12）与 Holm 校正、清洗向前滚动（`label_end = decision_time + 2d`、初始训练 365、测试 90、禁运 1 天、最少训练 30、留出期起点 `2026-01-02T16:00Z`）、成本闸（0.05% 单边、0.10% 翻转、循环分块自助法块长 10 / 2000 次 / 种子 42）。
   - 研究代码全部方法参数写死在代码中，只使用内置类型与受允许的 9 个模块，无任何属性赋值或删除，仅通过 `BlindMetrics` 把原始统计量交给内存中的框架比对器。
   - 在 `tests/test_btc_eth_001_rehearsal.py` 完成全链路合成数据彩排（覆盖空信号判 `一致`、植入强信号判 `不一致`、缺口/重复/非法收盘价清洗、截止日后价格突变零前视、逐字节确定性及盲输出防泄密检查）。
4. **前移方案 B（子进程隔离运行）期限**：
   - 将决策 0031 登记的下一里程碑 **方案 B（无凭证、断网、经 JSON/Parquet 窄管道通信的子进程隔离运行）** 的硬期限前移至：**首次在真实烧毁数据上消耗金库批准运行 `btc_eth_001`（`H-0010`）之前**（同样覆盖任何后续新研究代码合并之前）。
   - 本 PR 合并后立即启动方案 B 的决策记录与实现，不提前提交 `H-0010` 真实假说卡与金库批准；待方案 B 合入且 2026-11 月度归档到齐存储桶后，再开小 PR 登记 `H-0010`、锁定三文件 `code_sha256` 的一次性批准与试验卡。

## 后果

- 不修改任何冻结文件（`U1.toml`、`config/`、`registry/inherited/`、`.github/workflows/`、`STAGE`、`docs/decisions/0001..0031` 均未改动），不新增第三方依赖，不入库任何第三方派生数值。
- `btc_eth_001.py` 合并进 `main` 后代码即进入定型期；未来签发 `H-0010` 批准时，`code_sha256` 将同时锁定 `btc_eth_001.py`、`blind.py` 与 `stats.py` 三个文件的原始字节。
- 若 12 月初数据提前到齐而方案 B 仍在最后审查阶段，因 N5 与三文件 L4 已全部并入 `main`，所有者届时可基于明确风险权衡决定多等一两天或另立决策记录先行运行。
