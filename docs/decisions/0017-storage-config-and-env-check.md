# 0017 存储配置写进仓库；新增环境自检工作流

- 状态：已接受
- 日期：2026-11-25
- 提出：Claude，所有者合并即批准

## 背景

所有者 2026-11-25 在 Cloud Shell 里跑完了开通脚本：项目 `self-quant-pro`，存储桶和联合身份都已建好。

原计划把脚本最后打印的三项值存成 GitHub 仓库的 Actions 变量。实际做时发现：智能体所在的网络代理不允许调用 Actions 变量的接口。改让所有者在网页上手工填，也有问题：以后的智能体既看不到这些值，也核对不了。这三项值都不是密钥。

另外两件事还没验证过：联合身份到底能不能用；GitHub 的运行器能不能访问 Binance 的公开数据（决策 0015 之后的交接记录里，置信度中）。越早验证，出了问题越好改。

## 决定

1. 三项值写进 `config/storage.toml`，工作流和代码都从这里读。这个文件按冻结文件管理，改动要有决策记录。
   - 公开的代价：任何人都能知道存储桶的名字。但存储桶禁止公开访问，没有权限的请求一律被拒绝。
   - 被拒绝的请求一般不收费（谷歌云存储的计费说明，置信度中）。
2. 新增 `.github/workflows/env-check.yml`，只能手动触发，用联合身份（不用密钥）做两项检查：
   - 存储自检：新建一个小标记文件，确认能读回；确认重复写入被代码拒绝，覆盖和删除被权限拒绝。
   - 确认 GitHub 的运行器能访问 Binance 的公开数据。日志只打印 HTTP 状态码。
   - 合并后由智能体触发一次，把结果告诉所有者。
3. 新增依赖 `google-cloud-storage`。它是谷歌官方的存储客户端，能直接使用联合身份；G1 的数据层本来就要用。
4. 存储层（`src/sqp/storage.py`）只增不改，有两种后端：
   - 本机目录：先写临时文件，再用硬链接放到正式名字下；名字已经被占用就失败。
   - 谷歌云存储桶：写入时带"同名对象不存在才写"的前提条件。存储桶的权限是第二道保险。
   - 自检写的标记文件放在 `_check/` 下，每次运行留下一个几十字节的文件，不删除。

## 后果

- 本 PR 同时更新：架构第 2 节（目录）和第 4 节（谷歌云的布局）、开通说明、所有者简报、交接记录。
- 存储桶总量的上限检查，在下载器的 PR 里做（决策 0015 第 4 条）。在每次写入时都列一遍存储桶，会让操作费用翻倍。
- 需要重新考虑的情况：自检发现覆盖或删除没有被拒绝。那说明权限设置不对，要先修好，再写入任何数据。
